# CM3070 Past Exam Practice

These are practice answers to the CM3070 Final Project past papers in `pastexams/`. Each question below is my own short paraphrase, not a copy of the exam text. Answers are grounded in the actual project: an NLP pipeline (Template 12.1, identifying research methodology in computing papers) that extracts a four-role methodology profile — TechnicalMethod, Task, Dataset, EvaluationMetric — from computing research papers, implemented across proto2 (sentence-level zero-shot classification, `report1`/`report3`) and proto3 (document-level, schema-guided LLM extraction, current prototype), and documented in `report3/report.md` (completed draft) and `report4/report-memo.md` (final report in progress).

## Example Exam

### Q1. Rate three references you used as high/medium/low quality and justify each rating.

Jain et al. (SciREX, ACL 2020) is the highest-quality reference I used. It is peer-reviewed at a top NLP venue, built from 438 papers annotated by four PhD-level annotators with 95% inter-annotator agreement, and its four entity types — Dataset, Metric, Task, Method — map almost directly onto the four roles this project extracts. Oates's *Researching Information Systems and Computing* (SAGE, 2006) is a medium-quality reference: it is a properly published, widely used research-methods textbook, but it is written for human researchers to classify their own work, not to support automatic extraction from already-written papers, so its concepts need reinterpretation before they apply to my task. The least reliable reference I relied on is Ghosh et al.'s 2023 arXiv preprint (arXiv:2311.03401), which I treat as lower quality mainly because it is the unreviewed preprint version of work the same authors later published, in revised form, at CIKM 2023. I use the preprint only for early motivation (that methodology-component names are hard to extract because they are fast-evolving and context-dependent) and rely on the peer-reviewed CIKM version for anything I state with more confidence.

### Q2. Describe three significant moments or setbacks in the project and how you handled them.

The first was discovering, while evaluating proto2, that sentence-level zero-shot classification produced 151 candidate TechnicalMethod sentences for the MapReduce paper alone — far too many to be usable. Excluding sections by heading (Related Work, then the Introduction) reduced the count but also removed sentences that correctly described the paper's own method, so I stopped tuning the sentence classifier and redesigned the task as document-level extraction instead. The second was a Gemini API failure: calling `response_schema=MethodologyProfile` returned `400 INVALID_ARGUMENT ... Unknown name "additional_properties"`. I traced this to Google's `Schema` proto not supporting `additionalProperties`, which Pydantic's `extra="forbid"` produces, and fixed it by switching to `response_json_schema` with a raw JSON Schema dict. The third was a subtler shape bug: early testing on "Attention Is All You Need" showed Gemini returning the `evidence` field as one flattened string with the section heading prepended, instead of the nested `{section, quote}` object the design needed. I first patched this by rewriting the prompt; once `response_json_schema` was in place, the schema itself guaranteed the nested shape regardless of prompt wording, turning a bug I had to keep watching for into something structurally prevented.

### Q3. Evaluate your project process: two good aspects, two needing improvement, and two you would change.

Two things went well. First, redesigning the evaluation from proto2's recall-only substring check into Precision/Recall/F1 with Wilson 95% confidence intervals, which let me state uncertainty at a six-paper sample rather than overclaim from a single run. Second, enforcing the output schema through Pydantic models and `response_json_schema` rather than describing the JSON shape in the prompt text, which removed an entire class of parsing bugs by construction instead of by patching each one as it appeared. Two things needed improvement. First, I wrote both the gold labels and, later, the answers checked against them, so the whole evaluation carries a single-annotator bias I cannot fully correct for inside this project. Second, the four-role schema itself is ML-benchmark-shaped, inherited from SciREX's ML-conference corpus, and the manual review confirmed it fits the two systems papers in my six-paper set (MapReduce, PageRank) worse than the four ML papers. If I could improve two things, I would recruit even an informal second annotator for the gold labels and the manual review, rather than relying on the NotebookLM cross-check as my only independent signal; and I would test the schema against non-ML-benchmark papers earlier in the project rather than leaving it as further work, since proto2 had already hinted at the systems-paper weakness.

### Q4. What pre-existing knowledge did you bring, what new areas did you learn, and how?

I had already taken the module's Natural Language Processing course before starting this project, which is why Template 12.1 (identifying research methodology in computing papers) was open to me and shaped which project I chose. I also brought general software-engineering practice — static typing, automated tests, linting — which I carried directly into this project's tooling (`pyright` in strict mode, `ruff`, `pytest`). What I had to learn: zero-shot NLI classification with a DeBERTa-v3 model for proto2; GROBID-based PDF-to-TEI-XML parsing; schema-guided structured extraction from a long-context LLM using `response_json_schema`; and evaluation statistics, specifically Wilson confidence intervals for Precision and Recall, and why F1, being a harmonic mean rather than a proportion, does not get one directly. I acquired most of this by reading the primary sources directly (Oates, Jain et al., Yin et al., Dagdelen et al.) and testing each idea immediately against my own six-paper corpus — for example, I only understood why F1 cannot take a Wilson interval after first trying to compute one and finding it did not make statistical sense.

### Q5. Compare your chosen solution with two other routes you could have taken.

Two alternatives to proto3's joint document-level LLM extraction were staying with proto2's sentence-level zero-shot NLI classification, and moving straight to decomposed extraction — four independent per-role LLM calls (later built as Variant B for report4). I chose joint document-level extraction as the next design after proto2 because proto2's concrete failures (output volume, no authorship mechanism) were already clear, and Khot et al.'s decomposed-prompting argument, while promising, risked losing the cross-role relationships a single joint call can exploit — for example, recognising "Transformer", "WMT", and "BLEU" together in one sentence. Sentence-level NLI is cheap and needs no LLM API cost, but has no document-level context and cannot enforce an authorship rule sentence by sentence. Decomposed extraction offers role-specific, easier-to-debug prompts in principle, but when I actually built and scored Variant B on 2026-08-28, it left Task's F1 unchanged and only incidentally improved Dataset. I grounded this comparison empirically rather than only theoretically, by running Variant B against the Variant A baseline on the same six papers with the same scoring code.

### Q1. What is a literature review for, what belongs in it, and what belongs in an appendix?

A literature review shows I understand what is already known and already tried, so the project is judged against the right baseline and the reader can see which specific gaps my project fills, rather than assuming no prior work exists. Material that directly informs a design decision or a comparison point belongs in it; material that is only generally related, or restates a point another source makes better, does not. As an example of material I included: Khot et al.'s decomposed-prompting paper, which I read specifically because it directly justifies the Variant B design decision, so it belongs in the review even though I found it midway through the project rather than at the start. As an example of material I left out: several general LLM-prompting blog posts and vendor documentation I read while working out the `response_schema`-versus-`response_json_schema` distinction were essential to getting the implementation working, but they are not research contributions, so I kept that material in the Implementation chapter's code explanation instead of the literature review. An appendix suits material that is genuinely supporting rather than argument-carrying — extended output too voluminous for the main text, or process evidence that shows work was done without needing to be read in full to follow the report's argument. I included two appendices on this basis: one with GitHub Projects roadmap screenshots showing the project's actual timeline, and one with the full extraction JSON for the five papers not shown in the main Implementation chapter, plus the gold labels and proto2 background counts used throughout the later chapters. I used them because the main-body word budget could not fit five more full JSON examples without pushing out analysis, but the raw evidence is worth keeping available for a reader who wants to check a specific paper's result directly.

### Q2. Which template did you choose, what was the technical challenge, and what was your solution?

I chose Template 12.1 (NLP module) because it let a solo project build a working extraction system without a labelled annotated corpus, which the closest related work generally requires. The technical challenge was getting a long-context LLM to return one authorship-correct, evidence-backed answer per role, in a fixed shape, rather than either an unstructured summary or, as proto2 showed, a long list of loosely scored candidate sentences. My solution: a five-stage pipeline — GROBID parses the PDF to TEI XML; the relevant sections are concatenated in reading order; a schema-guided prompt, including an explicit "authors' own work" rule, is sent to Gemini with `response_json_schema` built from a Pydantic `MethodologyProfile` model; the model's own `model_validator` enforces that an answer and its evidence are either both present or both null; the result is rendered as a role table with quoted evidence the reader can check directly. In detail, for a fellow student to reimplement this: the pipeline follows PDF → GROBID parse (failure surfaced to the user) → TEI section validation (empty or invalid sections skipped and logged) → Stage 1 section concatenation → Stage 2 schema-guided LLM extraction (no supported answer returns `null` rather than a fabricated value) → a validated `MethodologyProfile` JSON object → the user-facing role table and quotes. The `Evidence`/`RoleExtraction` Pydantic models carry the null-correlation validator; the Gemini call uses `temperature=0` and `seed=0` for reproducibility; and using `response_json_schema` rather than `response_schema` is what makes the call succeed at all, since Google's own `Schema` proto does not support the `additionalProperties` field Pydantic's `extra="forbid"` produces.

Results: TechnicalMethod is the strongest role (F1 0.83, stable across all five runs); Task is the weakest (F1 0.33, also stable, and unmoved by the later Variant B experiment); Dataset and EvaluationMetric sit in between. I presented results as markdown tables plus direct notebook screenshots of the scoring cell running, so a reader sees the computation happen rather than trusting a transcribed number alone. Project materials: git version control, a public GitHub repository with pull-request-based history, a Colab notebook (which autosaves to Google Drive) mirrored into an installable package kept in sync by `sync_generated.py`, and results logged as JSON files rather than kept only as notebook output. If I did this again, I would log every experimental run — including ones I ultimately cut, such as the Related Work ablation — to a results directory from the start, rather than deciding after the fact which runs were worth keeping.

### Q4. Briefly describe what you achieved, your best achievement, and your weakest part.

I built two working prototypes that produce a four-role methodology profile from a computing paper — proto2 (sentence-level zero-shot NLI) and proto3 (document-level, schema-guided LLM extraction) — with proto3 backed by a classification-style evaluation across six papers. My single best achievement is the schema-guided extraction design, because it directly fixed both of proto2's structural problems — output volume and the lack of an authorship rule — rather than only mitigating them, and it is the one part of the project a fellow student could reuse against a different four-role schema. To reach better quality here, I would pair a dedicated Task-authorship check with a semantic-similarity scoring metric, rather than assume decomposition alone would fix it, since the actual Variant B result showed it did not.

### Q5. Would you advise a rewrite, what two things should a follow-on student add, and how should they approach it?

I would not advise a full rewrite. `pyright` in strict mode and `ruff` report zero issues, the `pytest` suite covers the scoring logic and the null-correlation validator, and `sync_generated.py` keeps the notebook and the installable package aligned, so the codebase is usable as it stands. I would advise one targeted addition first: implement the `MultiRoleExtraction` schema for Dataset and EvaluationMetric — a design already considered but not implemented — since BERT's Dataset and EvaluationMetric gold-label disagreements in the manual review trace directly to this single-valued limitation. Two things I would have a follow-on student include: first, a semantic-similarity scoring metric alongside the current substring match, since Task's low F1 is partly a measurement-instrument artefact rather than purely a model failure, and Variant B already showed decomposed extraction alone does not fix it; second, a small non-ML-benchmark case study — one HCI or systems paper beyond MapReduce and PageRank — since the manual review shows the schema fits ML papers better than systems papers, and this remains genuinely untested. ### Q1. Reflect on your planning phase: objectives, how you organised the early stages, and how effective the plan was.

What I would improve: the original evaluation plan, a simple gold-label substring match, had to be redesigned mid-project into the Precision/Recall/F1-with-confidence-intervals approach actually used, so next time I would build the statistically defensible evaluation method from the start. Objectives did change once concretely: the decomposed-extraction and multi-valued-role work, originally planned as report3 stretch goals, were cut from report3 for time, and only the decomposed-extraction pilot (Variant B) was picked back up for report4.

### Q2. Identify your most significant technical challenge, your solution, and evaluate its effectiveness.

The most significant technical challenge was authorship attribution: proto2 had no mechanism to separate a paper's own method from one it only cites — a sentence describing ELMo in BERT's Introduction scored 0.87 as TechnicalMethod, even though ELMo is prior work. This connects directly to the project's overall goal, since a methodology profile that credits the wrong paper is not trustworthy, whatever else it gets right. My solution was an explicit "authors' own work" rule inside proto3's Stage 2 prompt, combined with document-level context so the model sees enough of the paper to judge authorship rather than one sentence in isolation. Evaluating its effectiveness: the rule is addressed by design but not reliably solved — the manual review found 6 of 22 scored slots still fail the authorship check, concentrated in Task across four of the six papers. This met my expectations only partially: it clearly improved on proto2, which had no mechanism for this at all, but I would consider a dedicated authorship-classification sub-step, rather than a single prompt instruction, as an alternative approach if I revisited this.

### Q3. Discuss the two most significant references you used.

Jain et al.'s SciREX (ACL 2020) is the first. Its main contribution is a document-level information-extraction dataset and task defining four entity types — Dataset, Metric, Task, Method — that map almost directly onto this project's four roles. It was significant because it directly supplied both the schema and the argument for reading a whole document rather than single sentences, which shaped Chapter 3's design and Chapter 5's critical evaluation (its ML-conference corpus explains why the two systems papers in my own six-paper set fit the schema worse). Its quality is high: peer-reviewed at a top NLP venue, with a stated 95% inter-annotator agreement, though its scope — ML-benchmark papers only — is a limitation this project inherits. Khot et al.'s "Decomposed Prompting" (arXiv:2210.02406) is the second. Its main idea is that decomposing a complex task into independently optimisable subtask prompts can outperform a single joint few-shot prompt on several reasoning tasks. It was significant because it is the direct justification for building Variant B — four independent per-role extraction calls — specifically to target Task, the weakest role. Its quality is more mixed than SciREX's: it was an arXiv preprint at the time I relied on it, so I treated its claim as a well-supported hypothesis to test on my own data rather than an established result for this specific task — which is exactly what the Variant B experiment did, and its result (Task's F1 unchanged) shows the hypothesis did not transfer to this project's setting.

### Q4. Discuss the future impact, expansion, and advice for continuing this project.

In the medium term, a working four-role extractor could shorten the first pass of a literature review for a computing student starting a new topic, which was the original user need in Chapter 1. In the longer term, if extended to a wider paper corpus with a validated multi-valued schema, it could support a small structured index of methodology profiles across a reading list, letting a user compare methods, datasets, and metrics across many papers at once rather than one paper at a time. Concrete ways it could be expanded: the consolidation experiment (Variant C) that report4's decision gate skipped once Variant B alone did not help Task, since consolidation is a genuinely different, untested mechanism from decomposition alone; the multi-valued-roles schema for Dataset and EvaluationMetric with per-item evidence, motivated concretely by BERT's own manual-review failures; and testing on a larger, genuinely non-ML-benchmark corpus, since the current six-paper set is dominated by ML-benchmark structure. My main advice: do not assume a fix targeting one role will move that role's score just because the reasoning behind it is sound — Variant B's role-specific prompt reasoning was plausible and still made no measurable difference to Task. I would also advise validating any new gold label or scoring change against a small held-out set before trusting it, since several of this project's own apparent "failures" turned out to be gold-label or metric artefacts rather than genuine model errors.
